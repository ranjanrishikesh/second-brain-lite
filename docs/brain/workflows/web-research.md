# Web-research workflow

Read `docs/brain/policies/web.md` and `docs/brain/policies/approvals.md` before acting.

## Capture receipt boundary

Every `snapshot-url` response carrying `result_manifest`, including rendered captures, must complete this boundary before processing handoffs, registration, or another snapshot. Retain the bounded response's result ID, revision, and counts, then run `./brain --json source consume-sync-result --result-id "$result_id"`. Require its `result_id`, immutable `manifest_path`, corpus revision, exact event counts, effect digest, and `handoff_delivery` to match the retained reference and snapshot revision. This production CLI verifies and drains the full event stream and writes a durable deduplicated receipt; it does not acknowledge, dispatch, mutate sources/wiki, install, or use network. Read `manifest_path` only as needed to preserve exact citation rewrites, newly activated source IDs, and coverage gaps; when non-null, use only receipt-bound immutable `handoff_delivery` for typed handoffs. Response samples do not establish completeness. Apply and deduplicate those effects by permanent `result_id`, durably record them, and only then run `./brain --json source acknowledge-sync-result --result-id "$result_id"`; acknowledgement requires that matching consumed receipt.

Do not acknowledge an incomplete, invalid, or unsuccessfully persisted result. If output or consumption fails, replay the same snapshot arguments to recover the same result; do not start a different capture or process its handoffs until verification, durable consumption, and acknowledgement succeed. Repeated acknowledgement is idempotent. A response without a verifiable result reference cannot authorize follow-up work.

## Research and capture

1. Stop before opening any public URL.
2. Explain the local evidence gap and ask for explicit approval for a bounded research event.
3. After approval, research candidates; distinguish viewed candidates from evidence actually used.
4. For a used source with an existing descriptor, run `./brain --json source snapshot-url --source-id "$source_id" --approval-event-id "$event_id" --approval-scope "$scope" --approval-note "$approval_note"`. Complete the capture receipt boundary before continuing.
5. For a used ad-hoc URL with no descriptor, separately run `./brain --json source snapshot-url --url "$url" --description "$description" --approval-event-id "$event_id" --approval-scope "$scope" --approval-note "$approval_note"`. Steps 4 and 5 are alternative forms for one source; complete the capture receipt boundary after either form.
6. After consumption but before acknowledgement, verify and read only a non-null receipt-bound `handoff_delivery`, never response handoff arrays, and durably apply/deduplicate its exact effects. Require every typed item to map to the consumed manifest handoff effect. Acknowledge the matching receipt before dispatch, registration, or another source mutation. If `handoff.kind == "extraction"`, create the representation only at the exact `.brain/agent-staging/<handoff-id>/...` scope and register it with `./brain --json source register-extraction --handoff-id "$handoff_id" --staging-path "$staging_path" --anchors-json "$anchors_json" --quality-state "$quality_state" --note "$note"`. If `handoff.kind == "rendered_web_capture"`, use the already approved browser event to export faithful serialized DOM, print-to-PDF, or downloaded claim-bearing bytes below `.brain/web-staging/<handoff-id>/...`, then run `./brain --json source snapshot-url --source-id "$source_id" --rendered-staging-path "$rendered_staging_path" --handoff-id "$handoff_id" --retrieved-at "$retrieved_at" --final-url "$final_url" --detected-media-type "$detected_media_type" --approval-event-id "$event_id" --approval-scope "$scope" --approval-note "$approval_note"`; append one `--redirect-url "$redirect_url"` per observed redirect, and complete the capture receipt boundary again before following the new delivery or result. Never send a `rendered_web_capture` handoff to `register-extraction`.
7. For a capture completed directly, verify that `SnapshotResult.active_representation` is non-null and matches that snapshot's source/content identity and corpus revision. After `register-extraction` succeeds, instead verify `data.registration.active_representation` and `data.registration.corpus_revision`, including the captured source/content identity and the persisted ledger derivation; the original `SnapshotResult` remains unchanged and its active representation may still be null. Follow any new typed handoff through the same receipt and registration boundaries. Before research, revalidate every used representation against the latest corpus revision; an earlier capture's revision need not equal the revision after later registrations or captures. If a faithful local active representation cannot be reached, stop and do not cite the browser material. Never persist unused candidates.
8. Against the new corpus revision, start exactly these three logical runs once each and in order: `./brain --json search --scope sources --pass discovery --term "$discovery_term" --context 3`; `./brain --json search --scope sources --pass expansion --term "$expansion_term" --context 3`; `./brain --json search --scope sources --pass verification --term "$verification_term" --context 3`. Repeat `--term` within the initial invocation, and drain each result with `./brain --json search --cursor "$next_cursor"` until `complete: true` before deriving the next pass. Stop with partial/unanswered status if any run is incomplete.
9. Persist only locally resolving citations through a staged wiki-apply manifest after fully draining link-candidate runs for every write/delete.
